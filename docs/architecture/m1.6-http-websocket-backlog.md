# M1.6 — HTTP 1–3 and WebSocket boundaries

> Ordered implementation backlog. Prepared 2026-08-25 under
> [D-2026-08-25-1](../spec/decisions.md). No network capability or identity
> move is claimed merely because this document exists.

## Exit statement

M1.6 is complete when one statically composed runtime can bind and execute
`HttpClient`, `HttpServer`, `WebSocketClient` and `WebSocketServer` beside
Process and File, while all of the following remain true:

- HTTP/1.1, HTTP/2 and HTTP/3 are interchangeable physical bindings of the
  same HTTP contracts, not node types;
- a Call has one terminal `exit`, while a Session has many
  messages and one terminal session `exit`;
- every external write is journaled first and every application-level inbound
  acknowledgement follows an accepted causal commit;
- bounded mailboxes propagate pressure to HTTP/QUIC/WebSocket flow control;
- real and Lab Drivers use the same ids, exchange shapes, correlation and
  typed terminal gates;
- hosted network dependencies do not enter `rastok-core` or any no-std build;
- the Codex gateway example can expose one WebSocket session per logical
  client session without using a socket id as application data.

## Architecture to preserve

```text
                                semantic / portable

 RKG node ──▶ ContractCatalog ──▶ plan { id, roles, exchange, ports, facts }
                                      │
                                      ▼
                              pre-journal binding
                                      │
               ┌──────────────────────┴──────────────────────┐
               │                                             │
      InboundConnectorDriver                    OutboundConnectorDriver
       proposes world facts                     performs sealed intents
               │                                             │
               └────────────── one shared Binding ───────────┘
                                      │
                           VM + journal + mailboxes

                                hosted / physical

                         NetworkEngine (bounded pump)
                    ┌─────────────┼──────────────┐
                 HTTP/1.1       HTTP/2        HTTP/3
                 Hyper selected Hyper selected quiche selected
                    └─────────────┬──────────────┘
                                  │
                         WebSocket message codec
                         tungstenite selected
```

There remain exactly two Driver roles. `ConnectorExchange` is an orthogonal
closed fact:

```text
Event      : external fact ──▶ one inbound root (no per-event exit)

Call       : request ──▶ out* / err* ──▶ exactly one exit

Session    : open ──▶ { world ◀── message* ──▶ graph } ──▶ exactly one exit
```

`Clock`/`Calendar` use `Event`; the four network contracts below exercise the
other two shapes. The runtime owns identity, admission, journal ordering,
timeout, close-once and routing. The network engine owns sockets, TLS,
protocol state, framing and flow-control progress. No third-party type crosses
that boundary. Event requires exactly the inbound role. Session requires an
outbound view (outbound-only or both-role), because that is where its
open/write/terminal observations enter the generic fold; a Session sheet that
cannot expose that view refuses before binding.

## Contract matrix

| Contract id | Roles | Exchange | v1 multiplicity |
|---|---|---|---|
| `rastok/http-client@1` | outbound | call | concurrent calls |
| `rastok/http-server@1` | inbound | call | concurrent admitted requests |
| `rastok/websocket-client@1` | both, shared state | session | one live session per Node instance |
| `rastok/websocket-server@1` | both, shared state | session | many accepted sessions |

HTTP response completion belongs to the inbound server call; it does
not create a second outbound call. A WebSocket write is different: arbitrary
messages may cross in both directions throughout one live session, hence both
Driver roles share its state.

## Session rules frozen before code

1. `SessionRef` is an opaque logical reference derived from the committed
   opening fact. It excludes socket addresses, descriptors, negotiated HTTP
   version and placement.
2. Every `out` message and the sole `exit` project the same logical reference
   as `meta.ext.session_id`. Direct descendants may reply by lineage; a
   root-mixing or stored path must use explicit `correlate`.
3. One complete text or binary WebSocket message is one envelope. Fragments,
   ping/pong and close-handshake frames never become application envelopes.
4. `codec = json | text | bytes` determines the `in`/`out` payload type. JSON
   uses the existing exact house reader/writer. A text frame under `bytes` or
   a binary frame under `text` is a typed protocol refusal, never coercion.
5. Each graph-to-world message gets a journaled write intent before network
   bytes. Its local write settlement is not an application `exit`.
6. Exactly one typed session `exit` terminates the session; no `out` may
   follow it. There is no implicit `err` port.
7. Reconnection and application-message retry are explicit graph policy.
   Crash recovery never blindly replays an externally ambiguous message.
8. Buffer and message limits are finite contract/deployment facts. Mailbox
   full pauses protocol progress instead of allocating an unbounded side
   queue.
9. A server correlator resolves only a live session owned by that Connector.
   Peer data cannot seed or override `meta.ext.session_id`; an unknown/closed
   target is discarded-and-journaled as an orphan write, never misrouted and
   never turned into a second session exit.

The exact `WebSocketExit` cases and payloads are frozen in H2. At minimum they
must distinguish clean peer close, handshake rejection, protocol failure,
transport loss, timeout and the existing closed empty `OutcomeUnknown`, while
keeping OS/library strings out of causal payloads.

## Dependency posture

The implementation does not reimplement HTTP, QUIC, TLS or RFC 6455.

- `quiche 0.29.3` is the presumptive HTTP/3 backend. The isolated spike proves
  API shape, verified TLS, ALPN and stream correlation, not production
  readiness.
- Hyper is the presumptive HTTP/1.1-2 engine. Tokio may supply readiness only
  inside the hosted Driver assembly.
- Tungstenite is the presumptive RFC 6455 message codec; its stream adapter
  over an HTTP/3 CONNECT stream must be proved rather than assumed.
- `h3` + Quinn is the one required comparison because it may unify the HTTP/3
  TLS stack with Rustls. The comparison is product-shaped, not another toy
  throughput benchmark.

The adoption record must name exact versions, MSRV, licenses, default and
selected features, transitive package count, native build requirements,
stripped-size delta, TLS root/certificate strategy, cancellation model and
removal/substitution strategy. HTTP/3 and hosted networking are optional
static Driver features; embedded/no-std targets link neither.

### H5 — Execute `HttpServer` ack and respond

**Landed 2026-08-27.**

**Generic Call checkpoint landed 2026-08-26.** Connector-origin roots carry
their exact source path in key 27. For a Call, the same bounded accepting
commit also carries the root-derived `InboundCallRef` and exact source
instance in key 28. The categorical inbound Call Driver view can then report
one typed completion; the VM commits it once as `l:reply` with transaction key
52, no OUTBOUND record and no fake mailbox cursor. A fake retained HttpServer
request proves commit-before-accept, source-instance routing through an
Operator and one final `exit`. Existing packages, semantic hashes and causal
traces do not move because the new keys occur only on new live facts.

The final gate adds the physical and policy work:

- Bind bounded listener accept loops for HTTP/1.1, HTTP/2 and HTTP/3 to the
  generic proposal/Call protocol.
- `ack` sends 202 after commit, never before. `respond` holds one bounded
  request obligation, routes by lineage or explicit correlation, and emits
  the specified timeout/overload response exactly once.
- Map HTTP/1.1 connections, HTTP/2 streams and HTTP/3 streams onto the same
  Call protocol and backpressure contract.
- Prove malformed/auth/overload/timeout/disconnect races and orphan responses.
- Run blocking, hermetic server interop against pinned Caddy/NGINX and client
  interop through curl plus the nghttp2/ngtcp2 tools. Public Cloudflare/Google
  probes are scheduled canaries only, never a release gate.

**H5.1 checkpoint landed 2026-08-26.** D-2026-08-26-6 attaches the exact
ack-mode sheet to one live bounded Hyper listener for HTTP/1.1 and HTTP/2.
Listeners, routes, static settings and optional Rustls identities resolve
before the hosted thread starts. Connection count, H2 concurrent streams,
request count, event count and bytes are finite; body permits are acquired
before copy and remain owned by the retained proposal until the admission
decision. A full mailbox therefore withholds 202 and applies protocol
backpressure without a second queue. Real loopback H1 and H2 clients prove
that 202 follows the accepting commit and that both versions close the same
root-derived Call exactly once. Pre-admission auth/codec/body refusals create
no fake Call, and a later pending proposal cannot mask an earlier terminal
event. No identity register moves.

H5.1 deliberately leaves HTTP/3, `respond`, bounded request deadlines,
disconnect/write races, standalone runner polling and independent interop to
the remaining H5 gate. It also exposes the published-but-unreachable
pre-admission `HttpServerExit` cases for final-H5 contract cleanup rather than
fabricating causal facts.

**H5.2 checkpoint landed 2026-08-27.** D-2026-08-26-7 makes a graph delivery
to an inbound-only Call Connector the return half of the already-open Call,
not a new outbound effect. Direct lineage selects the exact opening source
instance before the response-producing transaction commits, including when
the Connector is keyed and the transformed response payload would select a
different key. Only after that commit does the registry offer the retained
response to the Driver. `Pending` writes no protocol bytes and keeps the
ordinary Connector mailbox claimed; `Started` transfers the bounded attempt,
whose typed terminal observation commits `l:reply` with the response's one
real cursor. Fixed ack keeps the zero-cursor form. Late, duplicate and
unmatched responses commit a consume-only discard, and neither path creates
an OUTBOUND record. The split request-output/response-input boundary also
keeps the executable dependency graph acyclic without a VM contract-name
branch.

H5.2 deliberately left the public HttpServer sheet in `mode = ack`. Final H5
lands the live response writer, explicit direct-path `correlate` selection,
timer-kind-8 request deadline and response/timeout close-once race together.
HTTP/1.1, HTTP/2 and HTTP/3 all use the same retained Call. The standalone
runner polls inbound Drivers without requiring stdin. Pre-admission framing,
authentication and body refusals create no fake Call; the corresponding
impossible exit cases are removed, moving only HttpServer semantic/package
identity (`63a257e2… → b83fcf2d…`) while prior causal facts remain fixed.

**Exit:** a remote client cannot observe acceptance for an uncommitted root,
and no request receives two responses across any supported HTTP version.

### H6 — Execute WebSocket Client and Server sessions

**Landed 2026-08-27.**

- Implement HTTP/1.1 Upgrade, HTTP/2 Extended CONNECT and HTTP/3 Extended
  CONNECT behind one session protocol.
- Prove text/binary/JSON messages, fragmentation, ping/pong, clean/unclean
  close, message limits, slow peers, simultaneous sends and close races.
- Prove server multi-session routing and client one-session-per-instance
  lifecycle using logical `SessionRef`, never socket identity.
- Prove journal-before-write, commit-before-explicit-application-ack, bounded
  receive flow, no blind replay and exactly one terminal `exit` per session.
- Make `codex-websocket-gateway.rkg` executable in the Lab and, with a real
  browser/CLI peer, as an integration test.
- Run the RFC 6455 surface in both client and server roles through the pinned
  Autobahn Testsuite, with a Node `ws` or browser peer as an independent
  smoke test. Extended CONNECT must be exercised by a stack other than
  Rastok's own client/server pair.

**Checkpoint:** D-2026-08-27-2 binds both WebSocket sheets to one generic
Session fold. HTTP/1.1 Upgrade, RFC 8441 HTTP/2 Extended CONNECT, and RFC 9220
HTTP/3 Extended CONNECT share one logical `SessionRef`, complete-message
codec, bounded Driver pump, journal-before-write rule, and sole `l:exit`
terminal. A server owns many correlated sessions; a client owns at most one
live session per Node instance. The VM bounds pending write obligations by the
ordinary Worker mailbox capacity, so a slow Driver cannot turn the durable
write table into a second unbounded queue. Tests cover text/binary/JSON,
fragmentation, ping/pong, size refusal, clean/unclean close, concurrent peers,
crossed writes, pending openings, timeout, cancellation, and terminal races.

The Codex gateway runs through the real CLI with WebSocketServer and Process.
The independent blocking probe executes Node `ws` over HTTP/1.1 and
`hyper-h2` + `wsproto` over Extended CONNECT, each with a finite deadline.
Pinned Autobahn client/server configurations are supplied for the official
container image. The reference Apple host has no container engine, so this
checkout does **not** claim an Autobahn HTML report; that external release
qualification must run on a container-capable host rather than being replaced
by an unofficial Python 3 port.

**Exit:** two concurrent Codex sessions cannot cross replies, a slow session
cannot allocate unbounded memory, and reconnect remains visible graph policy.

## Named limits after M1.6

- HTTP response streaming, SSE, WebTransport, HTTP datagrams and WebSocket
  extensions/compression are not smuggled into v1.
- Proxy/PAC discovery, HTTP cache policy, cookie jars and automatic
  application retries are separate contracts or policies.
- 0-RTT remains disabled until replay and idempotency are specified together.
- Native plugin ABI, out-of-process Driver hosting and hot reload remain the
  M1.5 future seam.
- Bare-metal networking is not a hidden requirement. A future embedded Driver
  may implement the same contracts over an explicit network stack, but M1.6
  does not add one to no-std builds.
