# M1.6 exit report — HTTP/1.1–3 and WebSocket Sessions

> Closed 2026-08-27. Normative authorities:
> [D-2026-08-25-1 through D-2026-08-27-3](../spec/decisions.md).
> Ordered implementation record:
> [`m1.6-http-websocket-backlog.md`](m1.6-http-websocket-backlog.md).

## Verdict

M1.6 answers its question positively: one statically composed hosted runtime
can bind and execute Process, File, HttpClient, HttpServer, WebSocketClient
and WebSocketServer through the same validated plan, Driver registry, VM,
journal and bounded-mailbox model.

HTTP/1.1, HTTP/2 and HTTP/3 are physical bindings of the same HTTP contracts.
A retained HTTP request is one Call. A WebSocket connection is one Session
with any number of complete messages and exactly one typed terminal `exit`.
Socket identity, negotiated protocol version, runtime library and physical
placement enter neither semantic identity nor logical correlation.

## The architecture that exited

```text
                       semantic / portable

 RKG Connector ──▶ ContractCatalog ──▶ validated v12 plan
                                              │
                                      exact pre-VM binding
                                              │
                  ┌───────────────────────────┴───────────────────────────┐
                  │                                                       │
       InboundConnectorDriver                               OutboundConnectorDriver
        proposes bounded facts                              performs sealed intents
                  │                                                       │
                  └────────────── one shared Binding ─────────────────────┘
                                              │
                                  VM + journal + mailboxes

                       hosted / physical

                  statically selected DriverRegistry
               ┌──────────────┬──────────────┬──────────────┐
            Process          File          HTTP          WebSocket
                                           │                 │
                                  ┌────────┼────────┐   complete-message
                               Hyper H1  Hyper H2  quiche H3  codec
                                  └────────┴────────┘   Tungstenite
```

The core exposes two Driver roles and three exchange lifecycles:

```text
Event    external fact ──▶ one inbound root; no per-event exit
Call     one request ──▶ ordered outputs ──▶ exactly one typed exit
Session  one open ──▶ messages in either direction* ──▶ exactly one typed exit
```

The hosted pump is private to `rastok`; no Tokio, Hyper, quiche, BoringSSL,
Rustls or Tungstenite type crosses a Driver interface or enters
`rastok-core`.

## Gate evidence

### H0–H2 — one model and four exact sheets

The source catalogue and Registry-free validator agree on four canonical
network ids, roles, exchange lifecycles, codec-selected ports, phased
settings, typed metadata and portable terminal unions. Categorical package
v11 introduced the closed Event/Call/Session fact; v12 later introduced the
open `media_type` scalar and expression constructor. Unsupported rows and
forged packages refuse rather than selecting a nearby behavior.

### H3 — one bounded hosted engine

One private current-thread pump owns independently bounded work, control and
fact lanes plus a shared byte budget. Hyper/Rustls supplies HTTP/1.1–2,
quiche/BoringSSL supplies HTTP/3, and Tungstenite supplies WebSocket message
framing. A real-UDP h3/Quinn comparison preserves a substitution path without
creating a second semantic boundary.

### H4 — live HttpClient and typed HTTP schema intent

The same HttpClient sheet executes over H1, H2 and H3. Exact request bytes and
their digest exist before OUTBOUND open; fallback ends before peer-visible
bytes; response bodies remain bounded; status, headers and content type return
as typed observations; every Call closes once. OpenAPI 3.0/3.1 projection
updates only deterministic generated Rastok source and reparses it through the
real compiler.

### H5 — live HttpServer Calls

HTTP/1.1, HTTP/2 and HTTP/3 listeners share one retained inbound-Call
protocol. Acceptance follows causal commit. `ack` sends 202 only afterwards;
`respond` retains one ordinary response cursor, supports explicit correlation,
arms a bounded request deadline and closes response/timeout races once.
Standalone `run` polls inbound Drivers without depending on stdin.

### H6 — live WebSocket Sessions

HTTP/1.1 Upgrade, RFC 8441 HTTP/2 Extended CONNECT and RFC 9220 HTTP/3
Extended CONNECT all bind to one generic Session fold. A server owns many
correlated sessions; a client owns at most one live session per Node instance.
Each inbound complete message follows bounded two-phase admission; each
outbound message is journaled before bytes; local write settlement is not an
application exit; only `l:exit` closes the Session.

The generic Session battery covers concurrent opens and writes, correlation,
pending starts, ambiguity, close-once, exact terminal typing and post-exit
silence. Hosted tests cover text, binary and JSON messages, fragmentation,
ping/pong, clean and unclean close, message limits, timeout, cancellation,
transport loss, simultaneous sends and multiple server peers. Pending durable
writes are charged to the ordinary Worker mailbox bound, so they cannot become
an unbounded second queue.

[`codex-websocket-gateway.rkg`](../examples/codex-websocket-gateway.rkg) runs
through the real CLI with WebSocketServer and Process.

### H7 — static composition and closure

`hosted_registry` is the single shipped assembly. Process is always present;
File appears only with an explicit physical root; network families follow
orthogonal Cargo capabilities. The full hosted image registers all six
families exactly once. A reduced image refuses a plan needing an omitted
Driver during global binding, before VM or journal construction.

The capability manifest is the exact data-only projection of that linked
registry. It freezes neither a Rust/native plugin ABI nor an artifact-loading
protocol.

## Interoperability evidence

Hermetic Rust integration tests exercise both sides of every supported HTTP
and WebSocket binding. An additional blocking probe under
[`spikes/websocket-interop/`](../../spikes/websocket-interop/) drives the real
Rastok gateway through two stacks not used internally:

- Node `ws 8.21.3` over HTTP/1.1 Upgrade (`NODE_WS_OK`);
- Python `hyper-h2 4.3.0` plus `wsproto 1.3.2` over RFC 8441 Extended CONNECT
  (`H2_EXTENDED_CONNECT_OK`).

Both probes have finite five-second deadlines. The directory also contains
pinned official Autobahn client/server configurations. The reference Apple
host has no container engine and the maintained Autobahn runner is shipped as
a frozen PyPy 2 container, so this closure does **not** claim an Autobahn HTML
report. That release qualification remains an explicit run on a
container-capable host; it was not replaced by an unofficial Python 3 port.

## Named limits

- The official Autobahn client/server report is an external release
  qualification still to run on a container-capable host.
- HTTP response streaming, SSE, WebTransport, HTTP datagrams and WebSocket
  extensions/compression are not in the v1 contracts.
- Proxy/PAC discovery, cookie jars, HTTP caching and automatic application
  retries remain separate policies or contracts.
- 0-RTT remains disabled until replay and idempotency are specified together.
- Hosted HTTP/3 server assembly currently comes through the full
  `hosted-network` image; `hosted-http3` alone intentionally supplies only
  the H3 client because the server also needs the shared H1/H2 listener
  assembly.
- No native plugin ABI, dynamic loader, out-of-process Driver host, hot reload
  contract or bare-metal network stack is claimed.

M1 continues with the Loop aspect, cost counters, `--watch`, and the
gallery/demo closure.
